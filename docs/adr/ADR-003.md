# ADR-003 — Delivery semantics: at-least-once + platform exactly-once intent

**Status:** Accepted · **Date:** 2026-09-02

## Context
Retries are inevitable (network blips, worker crashes, store windows). Options:
(a) at-most-once — silently lose work; (b) exact-once end-to-end — requires transactional
agreement with every external system (impossible generally); (c) at-least-once with idempotency.

## Decision
- **Delivery:** at-least-once to executors (leases, attempts, checkpointed offsets).
- **Apply:** exactly-once *intent* — every unit of work carries a deterministic idempotency key
  (`namespace/workflow/node/attempt` or `topic/partition/seq`); executors are contractually
  required to make side-effects idempotent (documented, enforced by examples + tests).
- **Ambiguity bound:** a crashed worker's effects window is bounded by lease TTL; renewal is
  refused past TTL/2 so the double-run window is always ≤ TTL.
- **Outbox pattern:** provided via `attempt`/`dlq` records for systems needing transactional
  publish (documented in `03 §9`).

## Consequences
+ Simplicity, testability, and the strongest achievable guarantee without external transaction
  protocols.
− The *task author* bears idempotency of external side effects — a contract we document and
  template (see `examples/`).

## Revisit triggers
A consumer requiring true exogenous exactly-once with a transactional DB — add outbox adapter.
