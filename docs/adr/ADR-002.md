# ADR-002 — Persistence: SQLite (WAL) behind a narrow store port

**Status:** Accepted · **Date:** 2026-09-02

## Context
We need durable, crash-safe, auditable storage for ~10 record kinds, single-writer semantics, and
zero operational burden for a v1 that must run "anywhere" (laptop, container, small VM).

## Decision
- Default adapter: **SQLite**, `journal_mode=WAL`, `synchronous=FULL` (fsync on commit → no loss on
  kill), `busy_timeout`, single writer task.
- The `Store` port stays **12 methods** (specify in `ports/store.py`) so Postgres is a drop-in:
  headers, tuples, ops, none leak SQL.
- Read path: immutable in-memory snapshots invalidated on write (single RW lock); 100k records cold
  start < 2 s (NFR-4 test).

## Consequences
+ Zero deploy surface; WAL gives the same crash guarantees as a hosted DB for single-writer.
+ Portability: file sits next to config; k8s needs one emptyDir (or PVC) volume.
− Not multi-node: two hosts cannot share an SQLite file safely. Multi-node = Postgres adapter +
  lease leader (ADR-004); documented as the v2 boundary, not a hidden limitation.

## Revisit triggers
> 1 node wanting HA; store file > 10 GB; concurrent multi-process reads across hosts.
