# ADR-005 — Concurrency: single process, single writer, snapshot reads

**Status:** Accepted · **Date:** 2026-09-02

## Context
Planes share state (workloads, leases, offsets). Naive threads → locks → deadlocks/races;
multi-process → shared store coordination; microservices → ops burden and cross-plane consistency
problems for a v1 whose planes are 90% one CPU.

## Decision
- One process; **one writer thread** owns every mutation (serialized queue, reentrancy-safe:
  a write issued from inside the writer runs inline — no self-deadlock).
- Reader threads (API, status) take the current `Snapshot` object; the writer replaces the
  snapshot reference atomically after each commit.
- Dedicated loops (scheduler, scaler, workflow, events, cron, leader, watchdog) as threads that
  submit writes through the queue — deliberate, bounded, observable.
- The `Store` port stays synchronous-simple for tests; the writer owns serialization.
- Measured before splitting (metrics per plane) — the split is then an adapter change, not a
  rewrite.

## Consequences
+ Race-free by construction; deterministic replay; tiny footprint; trivial local dev.
− One process is a single point of failure *per store* — mitigated by lease leader (ADR-004) and
  Supervisord/k8s restart; horizontal split is the documented v2 path.

## Revisit triggers
Any plane > 50% CPU sustained for a week; multi-team ownership of planes.
